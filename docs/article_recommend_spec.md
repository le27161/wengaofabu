# 用户个性化推荐文章接口 规格文档

## 目标

为前台门户提供"猜你喜欢"类推荐能力：每个用户看到的内容尽量不同，同时保证
最新发布与高热度文稿有更高概率被推荐。本次只交付后端接口，前端展示不在本规格范围内。

## 数据来源

- `articles`（status = published 的已发布文稿）
- `view_history`（登录用户最近观看记录，用于构建用户偏好画像）
- `user_actions`（action_type = dislike 的不感兴趣记录，推荐时排除）

## 接口契约

### GET /api/articles/recommend

可选登录（携带 Token 则个性化，未携带则按通用热门+新鲜推荐）。

**请求参数**

| 参数 | 类型 | 必填 | 默认 | 校验 | 说明 |
| --- | --- | --- | --- | --- | --- |
| limit | int | 否 | 8 | 1~20 | 返回推荐文稿数量，越界返回 422 |

**成功响应（200）**

```json
{
  "items": [
    {
      "id": 1,
      "title": "...",
      "summary": "...",
      "cover_url": "...",
      "view_count": 100,
      "like_count": 10,
      "favorite_count": 2,
      "share_count": 1,
      "categories": [{"id": 1, "name": "金融", "slug": "finance", "sort_order": 0}],
      "published_at": "2026-08-15 10:00:00"
    }
  ],
  "total": 8
}
```

响应字段复用 `Article.to_dict()`（不含正文/审核记录）。`total` 为实际返回条数
（候选不足 limit 时返回全部）。

**错误语义**

- 400：暂无任何已发布文稿可推荐
- 422：limit 不在 1~20 区间

## 推荐算法（四段式：向量召回 + 精排预留 + 热门兜底）

整体流程：

```
① 离线：全部文稿 → 向量模型 → article_embeddings 入库（已完成）
② 在线召回：用户向量 vs 内存全量文稿向量，KNN 取 top-50
③ 在线精排：top-50 → 特征 → 排序模型 → 重打分（预留，目前透传）
④ 兜底：过滤已观看/不感兴趣，候选不足时热门榜补齐，最终取 limit 篇
```

### 1. 向量内存缓存（冷数据加载 + 增量同步）

- 首次走到向量召回分支时，将 `article_embeddings` 全量载入进程内存：
  缓存结构为 `{article_id: {"hash": source_hash, "vector": np.ndarray}}`
- 后续请求增量同步：仅比对 `(article_id, source_hash)`（不读向量列），
  只加载新增或源文本变化的行，并清理已删除文稿的缓存——新写文稿/编辑文稿
  之后再次调用推荐会自动进入内存，无需重启进程
- 模型版本统一为 `embedding_service.MODEL_VERSION`（BAAI_bge-small-zh，512 维）

### 2. 用户分支判断

- 未登录或观看历史不足 20 篇：走通用推荐（见第 6 节）
- 登录且观看历史 ≥ 20 篇：走向量召回（用户向量与文稿向量同模型同文本规则）

### 3. 在线召回（KNN top-50）

- 取最近 20 条观看记录（`viewed_at` 倒序）
- 逐篇按与入库一致的文本规则 `build_article_text`（"分类1,分类2：标题"）调用
  同一向量模型（BAAI_bge-small-zh）向量化
- 按观看时长加权平均（权重 = 1 + watch_seconds/600），再 L2 归一化得到用户向量
  （注意力池化留作后续优化点）
- 用户向量与内存中全部已发布文稿向量做点积（双方均已 L2 归一化，即余弦相似度），
  取 top-50；相似度乘 `0.9~1.1` 随机扰动，保证每次召回结果/顺序不同
- 同时取出与用户向量相似度**最低**的 10 篇作为探索候选池（供第 5 节反信息茧房使用）

### 4. 在线精排（预留）

- `_rerank()` 目前原样透传 top-50
- 后续接入：对候选生成特征（相似度、热度、新鲜度、互动率等），调用排序模型
  重新打分排序

### 5. 兜底与输出

- 过滤已观看（`view_history`）与不感兴趣（`user_actions.dislike`）
- 过滤后不足 limit 篇时，按热度 `view + 3*like + 5*favorite + 2*share`（含随机扰动）
  从剩余已发布文稿补齐，补齐同样排除已看/不喜欢
- **探索位（反信息茧房）**：从探索候选池中排除已看/不喜欢/已入选后，
  按热度加权随机取 1 篇，放在推荐列表最后一位；最终返回
  `limit - 1` 篇相似内容 + 1 篇探索内容（探索池为空时返回 limit 篇相似内容）
- 最终返回 limit 篇（默认 8），探索位保证列表不全来自用户偏好

### 6. 通用推荐（未登录 / 历史不足 20 篇）

- 新鲜度 `fresh = exp(-age_days / 30)`，热度 min-max 归一化，
  偏好分取文章所属栏目中用户偏好最高的栏目权重
- 基础分 `base = 0.30 * 偏好 + 0.40 * fresh + 0.30 * hot`
- 随机扰动 `score = base * (0.75 + 0.5 * rand)`；贪心选取时同栏目已选篇数
  使该栏目剩余候选降权（`0.8 ** 已选数`），避免推荐全来自同一栏目
- 登录用户同样排除已观看与不感兴趣

## 前端交互

本接口为纯后端能力，前端（门户首页/相关推荐位）后续按需接入，不改变任何现有页面。

## 成功标准

1. 未登录调用返回推荐列表，条数 = min(limit, 候选数)，且全部为已发布文稿
2. 历史不足 20 篇的登录用户走通用推荐；历史 ≥ 20 篇走向量召回（两者都排除
   已观看与不感兴趣）
3. 向量缓存首次全量加载、之后增量同步，新文稿向量化后无需重启即可召回
4. limit 越界返回 422；无候选返回 400
5. 同一用户连续两次请求结果不一定相同（随机扰动生效）
6. `smoke_test.py` 新增对应断言并跑通
